========================================

1. WHAT THIS PROJECT IS
----------------------------------------
A falling-sand style physics sandbox for the owner's Android phone, played in
a mobile browser. You paint materials onto a grid; they fall, flow, burn,
freeze, dissolve, explode and combine. The aim is a toy you can mess about in,
where every material reacts with everything it physically should.

It is built with TypeScript and Vite. It deploys to GitHub Pages through a
GitHub Action. The original loose concept is in
/storage/emulated/0/particle-sandbox.txt — treat its steps as suggestions,
not requirements. The real specification is this file plus the reaction board.


2. DECISIONS ALREADY LOCKED IN
----------------------------------------
Do not re-ask these; the owner has settled them.

- Language: TypeScript, strict mode. Chosen because it catches typos in
  material names at build time.
- Build tool: Vite.
- Package manager LOCALLY: bun. Never npm. The owner's Termux/proot setup has
  had repeated npm cache failures (ENOENT rename errors). pnpm via corepack
  also failed to install. bun works and is already installed.
- Package manager IN CI: npm. That runs on GitHub's Linux servers, where npm
  is fine. This split is deliberate.
- Rendering: "hybrid split". Grains and solids render as crisp cells;
  liquids, gases and light get soft glow and trails.
- Roster size: 48 materials, every one reacting as widely as physically
  sensible.
- Play style: open-ended toy. No score, no levels. Paint, erase, pause.
- Controls: comfortable two-thumb. Element picker near the thumbs, brush size
  on a slider, large touch targets (44px minimum).
- Aesthetic: earthy elemental. Deep neutral backdrop so each material's own
  colour carries the scene. Not neon cyberpunk, not candy, not a specific
  "theme" costume. Nature plus a furnace.
- Low-reactivity materials are allowed and wanted, as long as they are
  deliberate: bedrock (build wall), obsidian (acid-proof), gold (inert),
  glass (transparent, stable), rust (end product), stone (base solid).


3. WHERE THE FILES LIVE
----------------------------------------
Two copies exist. This matters — read carefully.

  /storage/emulated/0/particle-sandbox/
      The owner's upload copy. This is what gets zipped and pushed to GitHub.
      Source files only. Do NOT try to build here.

  /root/particle-sandbox/
      The working copy. node_modules lives here. ALL local builds, dev

WHY: /mnt/sdcard (internal storage) is mounted noexec-ish and cannot run
native binaries. Vite's Rollup native module fails there with
"failed to map segment from shared object" (ERR_DLOPEN_FAILED), and esbuild
fails with EACCES. Copying the project to /root fixes both.

RULE: edit source in BOTH copies, or edit in /root then copy the changed
files to /storage. Keep them in step. Never let them drift.

6. THE REACTION MODEL
----------------------------------------
The single source of truth is tools/reaction-board.py. It defines, for every
material, a set of physical properties, then computes a reaction symbol for
all 1,128 pairs. Run it to regenerate the board images.

Properties per material (in the `m(...)` helper):
  state      solid | powder | liquid | gas | energy
  dens       density, used for floating/sinking
  heat       how much it melts others (0-3)
  melt       heat needed to melt this
  ignite     how readily it sets others alight
  chill      how much it freezes others
  fuel       how well it burns
  explode    detonates when lit
  conduct    conducts lightning/plasma
  inert      ignores everything (bedrock only)
  soluble    dissolves in water
  absorb     soaks up liquids
  acidic     corrodes acid-vulnerable things
  acidvuln   how vulnerable it is to acid
  freezable  can be frozen
  shatter    breaks under blast or lightning

Reaction symbols (7 + none):
  B  ignites / burns
  D  dissolves / corrodes
  M  melts / softens
  F  freezes / chills
  R  reacts into something new
  X  destroys / explodes / quenches / shatters
  ^  floats / separates by density
  .  no reaction

The script holds an explicit list (variable E) of 892 live hand-written pairs
with plain-English reasons, and a fallback rule engine for the rest. Fallback order:
inert check, explosion-when-lit, ignition, heat melt, chill freeze, acid,
dissolve, absorb, density separation, conduction.

Current coverage: 621 reacting pairs out of 1,128. The remaining 507 are true
"nothing happens" pairs.

Most reactive: Lava 45, Plasma 44, Molten Metal 44, Bomb 42, Lightning 42.
Least reactive (all intentional): Bedrock 0, Obsidian 7, Gold 9, Stone 13,
Glass 13, Rust 13.

IMPORTANT: the board is a design document. When the simulation is written,
the reaction data must be ported into TypeScript and must agree with the
board. If a pair behaves differently in the game than on the board, the board
is the intended behaviour unless the owner says otherwise.

8b. HOW UPLOADING WORKS
----------------------------------------
The owner uploads a zip, not loose files. Two workflows cooperate:

  unzip.yml   watches for any *.zip at the repo root. Unpacks it, copies the
              files over the working tree, commits them as
              "Unzip archive", and deletes the zip in the same commit.
              It skips .git, .github, node_modules, dist and nested zips.
              It refuses to run if the archive has no package.json or no
              src/ folder, so a bad upload cannot wipe the project.

  deploy.yml  then builds with npm and publishes dist/ to GitHub Pages.
              It triggers on the Unzip workflow finishing (workflow_run),
              not on a push, because the unpack's own commit is pushed with
              GITHUB_TOKEN and GitHub does not start workflows for those.

So the upload procedure is: put the zip at the top level of the repo, commit
and push. The rest is automatic. A build takes a minute or two.

Guard rails inside unzip.yml:
  - only .zip files at the root are considered
  - the shallowest package.json decides the project root
  - src/ and index.html must exist next to it, or nothing is copied
  - the bot's own commit does not retrigger the workflow
  - two unpacks on the same branch queue instead of racing


9. WHAT TO BUILD NEXT — IN THIS ORDER
----------------------------------------
Step A. Port the reaction data to TypeScript.
  - Create src/materials.ts exporting the 48 names as a union type and a
    record of properties. A typo must be a compile error.
  - Port the explicit pair list and the fallback rules from
    tools/reaction-board.py. Keep the same symbols and the same outcomes.
  - Verify: a script or test that reproduces the board's 621 reacting pairs
    and prints a diff of zero.

Step B. The simulation core.
  - A typed grid, width x height in cells, held in a Uint8Array or similar.
  - A fixed timestep tick. Bottom-up iteration for falling materials so
    particles do not fall more than one cell per tick.
  - Movement rules per state: powder falls and piles; liquid falls and
    spreads sideways; gas rises; energy rises and dies out.
  - Reaction pass using the ported data.
  - Keep it deterministic and testable. Pure functions where possible.

Step C. Rendering.
  - Canvas 2D first. One canvas, sized to the device pixel ratio.
  - Hybrid look: crisp 1-cell rects for solids and powders; for liquids,
    gases and energy, draw at slightly larger radius with low-alpha glow.
  - Only redraw changed cells if frame rate needs it; start simple and
    measure on the actual phone.

Step D. Touch controls.
  - Element picker along the bottom, thumb-reachable, scrollable.
  - Brush size slider. Eraser. Pause. Clear.
  - Large targets, no hover reliance, no text input.

Step E. Polish and ship.
  - Sound off by default. Pause when the tab is hidden.
  - Cap particle count with a visible indicator if it gets heavy.
  - Build, zip, upload, confirm GitHub Pages serves it.

Order matters. Do not start rendering before the simulation is correct, and
do not start the simulation before the material data compiles.

11. KNOWN GOTCHAS
----------------------------------------
- Building on /mnt/sdcard fails (Rollup native module, esbuild EACCES). Use /root.
- The deploy workflow no longer sets `cache: npm` because there is no
  package-lock.json (the local lockfile is bun.lock). npm install runs fresh
  in CI. Do not re-add the cache line without committing a package-lock.json.
- .gitignore exists and covers node_modules/, dist/, *.log, .DS_Store.
- There is no git repository yet in either copy.
- The owner's phone is narrow with a touch keyboard. Assume small viewport.
- unzip.yml deliberately refuses archives without package.json or src/.
  If an upload is rejected, read the workflow log: it prints the archive's
  full file listing so the cause is visible.
- deploy.yml is chained to unzip.yml with `workflow_run`. Without that chain
  the site would never update after an upload: bot pushes do not trigger
  other workflows. If you ever rename the Unzip workflow, update the
  `workflows: ["Unzip"]` line in deploy.yml to match exactly.
